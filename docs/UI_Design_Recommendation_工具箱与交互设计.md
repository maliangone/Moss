# 企业 AI Agent 平台 — UI 设计建议

## Enterprise AI Agent Platform — UI/UX Design Recommendation for Non-Technical Users

---

## 1. 设计原则

我们的目标用户是制造业公司50-100名非技术员工（市场、法务、财务、运营）。他们不知道什么是slash command、skill、MCP或agent。UI必须做到：

**「用户看到的是能力，不是技术概念」**

| 技术术语（隐藏） | 用户看到的（暴露） |
|-----------------|-----------------|
| `/skill-name` slash command | "📊 数据分析" 按钮 |
| Skill auto-trigger (description match) | Agent 自动选择最佳工具 — 用户无感 |
| MCP server connection | "已连接：钉钉 / ERP / 数据库" 状态指示 |
| Sub-agent delegation | "正在分析...（3个子任务并行中）" 进度条 |
| CLAUDE.md instructions | 用户永远看不到 |
| `settings.json` permissions | 用户永远看不到（管理员后台） |

## 3. 「工具箱」— 核心 UI 创新

### 问题

Claude Code 有 ~30 个内置 slash command + 自定义 skill 可能上百个 + MCP + sub-agent。在终端里输入 `/` 然后过滤对程序员没问题，但对非技术用户来说：

- 他们不知道有哪些能力可用
- 他们不知道该用哪个
- 他们不知道什么时候该手动触发、什么时候系统会自动触发

### 解决方案：三层触发机制

```
┌─────────────────────────────────────────────────┐
│            触发机制三层架构                        │
├─────────────────────────────────────────────────┤
│                                                  │
│  Layer 1: 自动触发（用户无感）                     │
│  ══════════════════════════                      │
│  Claude 根据 skill 的 description 自动匹配       │
│  用户说"分析这个数据" → 自动加载 data-analysis    │
│  用户上传 .xlsx → 自动加载 pandas/openpyxl       │
│  用户提到"预测" → 自动加载 ml-modeling skill      │
│                                                  │
│  UI表现: 仅在进度面板显示                          │
│  "⚙ 已启用技能: 数据探索分析"（小字，不干扰）     │
│                                                  │
│  Layer 2: 智能建议（用户可选）                     │
│  ══════════════════════════                      │
│  根据上下文弹出建议卡片                           │
│  类似 IDE 的代码补全 / 手机键盘的联想词            │
│                                                  │
│  UI表现: 输入框上方浮动建议                        │
│  ┌─────────────────────────────────┐             │
│  │ 💡 你可能想要:                    │             │
│  │ [📊 深度数据分析] [📈 预测建模]   │             │
│  │ [📋 生成报告]    [🔄 对比分析]   │             │
│  └─────────────────────────────────┘             │
│                                                  │
│  Layer 3: 主动选择（工具箱面板）                    │
│  ══════════════════════════                      │
│  用户主动打开工具箱浏览所有可用能力                 │
│  按部门/场景分类，带搜索                           │
│                                                  │
│  UI表现: 侧边栏或底部弹出面板                      │
│                                                  │
└─────────────────────────────────────────────────┘
```

## 5. 智能建议系统设计（Layer 2 详细展开）

### 5.1 触发时机

```
触发条件 → 建议内容
─────────────────────────────────────
用户上传 .xlsx/.csv 文件
  → [📊 分析数据] [🧹 清洗数据] [📋 生成报告]

用户说"预测"/"趋势"/"下个月"
  → [📈 趋势预测] [🔮 回归分析]

用户说"对比"/"比较"/"vs"
  → [🔄 A/B对比分析] [📊 同比环比]

用户说"报告"/"PPT"/"汇报"
  → [📋 生成分析报告] [📊 生成PPT] [📄 生成Word]

用户上传 PDF
  → [📄 提取PDF内容] [📊 分析PDF中的表格]

对话已产生分析结果
  → [💾 导出为Excel] [📋 生成报告] [📊 生成PPT]

上下文包含多个数据集
  → [🔗 合并数据集] [🔄 交叉分析]
```

```
┌──────────────────────────────────────────────┐
│                                              │
│  🤖: 我已经完成了销售数据的基础分析。         │
│      [查看完整结果 ▾]                         │
│                                              │
│  ┌──────────────────────────────────────┐    │
│  │ 💡 接下来你可以:                      │    │
│  │                                      │    │
│  │  [📈 预测下月趋势]                   │    │
│  │  [📋 生成完整报告]                    │    │
│  │  [📊 生成PPT给领导汇报]              │    │
│  │  [💾 导出Excel]                      │    │
│  │                                      │    │
│  └──────────────────────────────────────┘    │
│                                              │
├──────────────────────────────────────────────┤
│ 📎 上传  [🧰 工具箱 ▾]  [输入...]   [➤ 发送] │
└──────────────────────────────────────────────┘
```

**关键设计点**：
- 建议卡片出现在 Agent 回复之后、用户输入之前
- 点击即执行（等效于用户手动输入 slash command）
- 每次最多显示 3-4 个建议，避免选择疲劳
- 建议是上下文感知的，不是固定列表

## 6. 执行过程可视化

### 6.1 Claude Code 的 Sub-agent/Task 可视化

当 Agent 执行复杂任务时，Claude Code 内部可能会 spawn 多个 sub-agent 并行工作。用户不需要理解"sub-agent"，但需要看到进度。

**方案：任务树 + 进度条**

```
┌──────────────────────────────────────────────┐
│  🔄 正在执行: 销售数据深度分析                  │
│                                              │
│  ├─ ✅ 数据读取与清洗              (8秒)      │
│  │   └─ 修复了 23 个空值，去除 5 条重复       │
│  ├─ ✅ 基础统计分析                (12秒)     │
│  │   └─ 生成了 8 个指标的统计摘要             │
│  ├─ ⏳ 趋势分析与可视化            进行中...   │
│  │   └─ ████████░░░░ 65%                    │
│  ├─ ⏳ 异常值检测                  排队中      │
│  └─ ⏳ 生成报告                    排队中      │
│                                              │
│  预计剩余时间: ~45秒                          │
│  [⏸ 暂停] [🔍 查看详情]                       │
└──────────────────────────────────────────────┘
```

### 6.2 技能使用透明度（可折叠）


### 管理员可配置项

每个 Skill/MCP/Agent，管理员可以设置：

| 配置项 | 说明 | 示例 |
|-------|------|------|
| **可见部门** | 哪些部门的用户在工具箱中能看到此技能 | 全员 / IT+财务 / 仅生产部 |
| **触发方式** | 自动（description-match）、手动（工具箱/建议）、或两者 | 数据清洗=自动；ML建模=仅手动 |
| **工具箱分类** | 在工具箱面板中归入哪个类别 | 数据分析 / 预测建模 / 报告 |
| **显示名称** | 用户看到的名字（不是 skill 的技术名称） | "趋势预测" 而非 "ml-forecast" |
| **显示图标** | Emoji 或图标 | 📈 |
| **显示描述** | 一句话说明（给用户看） | "基于历史数据预测未来趋势" |
| **建议触发词** | 当用户输入包含这些词时，作为建议弹出 | "预测, 趋势, 下个月, forecast" |

## 10. 用户自创 Skill — 能力的动态扩展

### 设计转变

前面的设计假设"管理员配好一切，用户只消费"。但 Claude Code 最大的优势之一是：**用户可以让 Claude 帮自己创建 Skill**。这意味着平台的能力不是固定的——每个用户都能根据自己的工作场景动态扩展。

这改变了整个架构的定位：

```
旧假设: 管理员是能力提供者，用户是消费者
新架构: 管理员提供基础能力 + 安全边界，用户是共建者

┌─────────────────────────────────────────────────────────┐
│  共享 Skills（管理员管理）                                │
│  /shared/skills/                                        │
│  数据分析、报告生成、PPT、PDF、行业专用...                │
│  → 所有人（或指定部门）可用                              │
│  → 管理员安装/卸载/配置可见性                            │
├─────────────────────────────────────────────────────────┤
│  个人 Skills（用户自建）                                 │
│  /workspace/{user}/.claude/skills/                      │
│  用户自己的分析流程、报告模板、专属工作流...              │
│  → 仅该用户可用                                         │
│  → 用户通过对话创建，下次会话自动生效                    │
│  → 管理员可设置策略（允许/审批/禁止）                    │
├─────────────────────────────────────────────────────────┤
│  提升为共享（用户 → 管理员）                             │
│  用户创建了好用的 Skill → 提交给管理员                   │
│  → 管理员审核后放入 /shared/skills/                      │
│  → 全公司受益                                           │
└─────────────────────────────────────────────────────────┘
```

### 管理员安全策略

用户自创 Skill 带来灵活性，也带来风险。管理员需要设置策略：

```yaml
# /shared/config/skill-policy.yaml

user_skill_creation:
  enabled: true                    # 允许用户创建个人 Skill
  
  # Skill 内容限制
  allowed_patterns:
    - "*.md"                       # 纯 Markdown Skill（最安全）
    - "scripts/*.py"               # 允许 Python 脚本
  
  blocked_patterns:
    - "scripts/*.sh"               # 禁止 shell 脚本（高风险）
    - "**/*curl*"                  # 禁止网络请求类脚本
  
  # Skill 可使用的工具限制
  allowed_tools_in_skills:
    - "Read"
    - "Write(*.py)"
    - "Write(*.csv)"
    - "Write(*.xlsx)"
    - "Write(*.png)"
    - "Bash(python *)"
  
  blocked_tools_in_skills:
    - "Bash(curl *)"
    - "Bash(wget *)"
    - "mcp__*"                     # 个人 Skill 不可调用 MCP
  
  # 社区安装限制
  community_install:
    enabled: true
    allowed_sources:               # 仅允许从审核过的源安装
      - "anthropics/skills"        # Anthropic 官方
      - "K-Dense-AI/*"             # 已审核的科学计算
    require_admin_approval: false  # 白名单源不需要审批
    
  # 分享机制
  share_to_team:
    enabled: true
    require_admin_review: true     # 分享前必须管理员审核
```

### Skill 持久化架构（关键技术问题）

#### 问题

Claude Code 的 skill 发现路径是硬编码的：
- **Personal skills**: `~/.claude/skills/` — 即 `$HOME/.claude/skills/`
- **Project skills**: `{当前工作目录}/.claude/skills/`

在我们的多用户 Docker 架构中：
- 容器可能重启（skill 如果在容器临时文件系统中就会丢失）
- 多个用户共享同一个容器（`$HOME` 默认指向同一个 `/root` 或 `/home/claude`）
- 每个会话的"工作目录"是什么？是临时的还是持久的？

如果不解决这个问题，用户辛辛苦苦让 Claude 创建的 skill，下次登录就没了。

#### 解决方案：$HOME 重定向 + Docker Volume 持久化

**核心思路**：每个用户会话启动时，将 `$HOME` 环境变量指向该用户在持久化卷上的专属目录。Claude Code 的 `~/.claude/skills/` 自然就解析到持久路径。

#### 会话启动脚本

CloudCLI 启动每个用户的 Claude Code 会话时：

```bash
#!/bin/bash
# start-user-session.sh
# 由 CloudCLI 在用户登录时调用

USER_ID="$1"  # 例如 "zhangsan"
SESSION_ID="$2"  # 例如 "zhangsan-20260323-001"

# ===== 关键：将 HOME 指向用户的持久化目录 =====
export HOME="/persistent/users/${USER_ID}"

# 确保目录结构存在
mkdir -p "${HOME}/.claude/skills"
mkdir -p "${HOME}/.claude/projects"
mkdir -p "${HOME}/uploads"
mkdir -p "${HOME}/outputs"

# 创建临时工作目录
WORK_DIR="/persistent/temp/session-${SESSION_ID}"
mkdir -p "${WORK_DIR}"

# ===== Enterprise 级 Skills 通过 managed settings 注入 =====
# Claude Code 支持 enterprise managed-settings.json
# 路径: /etc/claude/managed-settings.json（全局只读）
# 其中可以配置 enterprise-level skill 路径

# ===== 启动 Claude Code =====
claude \
  --session-id "${SESSION_ID}" \
  --project "${WORK_DIR}" \
  2>&1
```

这样 Claude Code 内部的路径解析变成：

| Claude Code 概念 | 解析到的路径 | 持久性 |
|-----------------|------------|-------|
| `~/.claude/skills/` (personal) | `/persistent/users/zhangsan/.claude/skills/` | ✅ **持久** — Docker Volume |
| `~/.claude/CLAUDE.md` (personal) | `/persistent/users/zhangsan/.claude/CLAUDE.md` | ✅ **持久** |
| `~/.claude/projects/` (memory) | `/persistent/users/zhangsan/.claude/projects/` | ✅ **持久** |
| `{project}/.claude/skills/` (project) | `/persistent/temp/session-xxx/.claude/skills/` | ❌ **临时** — 会话结束可清理 |
| Enterprise managed settings | `/etc/claude/managed-settings.json` | ✅ **持久** — Docker 镜像内置 |

#### 用户视角：何时用 Personal vs Project

```
Personal Skill（持久，跨所有会话）
═══════════════════════════════
用户: "把这个OEE分析做成我的常用工具"
  → Claude 创建到 ~/.claude/skills/oee-weekly/
  → 路径实际是 /persistent/users/zhangsan/.claude/skills/oee-weekly/
  → ✅ 下次新会话自动可用
  → ✅ 容器重启后仍在
  → ✅ 出现在工具箱的「⭐ 我的技能」中

Project Skill（临时，仅当前任务）
════════════════════════════════
用户: 正在做一个复杂的 Q3 分析项目，中间创建了辅助 skill
  → Claude 创建到 {work_dir}/.claude/skills/
  → 路径实际是 /persistent/temp/session-xxx/.claude/skills/
  → ✅ 当前会话可用
  → ❌ 会话结束或清理后消失（除非用户明确保存）
```

在 UI 上，我们需要在 Claude 创建 skill 时**引导用户选择**：

```
┌──────────────────────────────────────────┐
│  ✅ 技能创建成功: 「Q3渠道对比分析」      │
│                                          │
│  保存为：                                │
│  ┌────────────────────┐                  │
│  │ ⭐ 常用技能（推荐） │ ← 持久，跨会话  │
│  │ 以后随时可以用      │                  │
│  └────────────────────┘                  │
│  ┌────────────────────┐                  │
│  │ 📂 仅本次任务       │ ← 临时          │
│  │ 只在当前分析中使用  │                  │
│  └────────────────────┘                  │
│                                          │
└──────────────────────────────────────────┘
```

默认选「⭐ 常用技能」——大部分非技术用户不理解"临时 vs 持久"的区别，给他们持久的就对了。

技术实现：「⭐ 常用技能」= 写入 `~/.claude/skills/`（即 `/persistent/users/{user}/.claude/skills/`）；「📂 仅本次任务」= 写入 `{work_dir}/.claude/skills/`。

#### 备份策略

```bash

# 只备份 .claude/skills/ 目录，不备份临时文件
```

### Skill 发现优先级

Claude Code 的完整优先级链：**enterprise > personal > project > plugin**

在我们的架构中：

| 层级 | 路径 | 管理者 | 持久性 |
|------|------|--------|-------|
| Enterprise | `/etc/claude/managed-settings.json` 中配置的路径，或 `/persistent/shared/.claude/skills/` | 管理员 | ✅ 持久（只读挂载） |
| Personal | `/persistent/users/{user}/.claude/skills/` (即 `~/.claude/skills/`) | 用户 | ✅ 持久（Docker Volume） |
| Project | `{work_dir}/.claude/skills/` | 会话 | ❌ 临时（可丢弃） |

同名 skill 时 enterprise 覆盖 personal 覆盖 project。这意味着管理员可以用 enterprise skill 强制统一某些行为，即使用户创建了同名的 personal skill。

## 11. Claude Code 能力四层架构与 UI 暴露原则

### 四层能力架构

Claude Code 的能力分成四层，每层的触发机制和可控性完全不同。理解这个分层是 UI 设计的基础。

```
┌─────────────────────────────────────────────────────────────────┐
│  第一层：内置工具（Tools）— 永远存在，Claude 自主决定用不用       │
│  ─────────────────────────────────────────────────────────       │
│  Read, Write, Edit, Bash, Grep, Glob, WebSearch, WebFetch       │
│  Agent（原名 Task）← 这是 spawn sub-agent 的入口                │
│                                                                  │
│  管理员控制: settings.json 的 allow/deny 规则                    │
│  用户感知: 完全无感，不需要知道这些工具的存在                     │
├─────────────────────────────────────────────────────────────────┤
│  第二层：内置 Sub-Agent — Claude 自主调度                        │
│  ─────────────────────────────────────────                      │
│  Explore  — 默认 Haiku，只读搜索，用于代码库/文件探索            │
│  Plan     — 继承主模型，只读，Plan mode 下理解项目结构            │
│  general-purpose — 继承主模型，全工具，复杂多步骤任务             │
│  claude-code-guide — 查 Claude Code 文档                        │
│  statusline-setup — 配置终端状态栏                               │
│                                                                  │
│  管理员控制: 不可卸载。可通过 CLAUDE.md 和 --max-turns 影响行为  │
│  用户感知: 只看到"正在并行分析..."进度树，不知道 sub-agent 存在   │
├─────────────────────────────────────────────────────────────────┤
│  第三层：Bundled Skills — 预装的 slash command                   │
│  ─────────────────────────────────────────                      │
│  /simplify — 三 agent 并行代码审查                               │
│  /skill-creator — 创建新 skill 的引导                            │
│  /docx, /pdf, /pptx, /xlsx — 文档生成/处理                      │
│  /frontend-design — 高质量前端界面生成                           │
│                                                                  │
│  管理员控制: 不可卸载，但可在 UI 层隐藏或映射为中文按钮           │
│  用户感知: 以"📊 生成PPT"等按钮形式出现，不知道是 slash command  │
├─────────────────────────────────────────────────────────────────┤
│  第四层：自定义 Skills / Agents — 管理员安装的                   │
│  ─────────────────────────────────────────                      │
│  社区 skills (K-Dense 科学计算、数据分析、行业专用等)             │
│  自研 skills (AOI质检、SPC分析、ERP查询等)                       │
│  自定义 sub-agents (在 .claude/agents/ 定义)                     │
│                                                                  │
│  管理员控制: 完全控制——安装/卸载/可见性/触发方式/部门权限         │
│  用户感知: 工具箱中的业务能力卡片                                 │
└─────────────────────────────────────────────────────────────────┘
```

### "深度调查"的真相：不是 Skill，是 Claude 的自主决策

当你让 Claude Code 做深度调查时，它会自动 spawn 多个 sub-agent 并行工作——这不是某个 skill 触发的，而是 Claude 通过**第一层的 Agent 工具 + 第二层的内置 sub-agent** 自主完成的：

```
你: "全面分析我们和竞品在东南亚市场的差异"

Claude 主 Agent 的决策（用户看不到）:
  → 任务复杂，需要多维度并行研究
  → spawn Agent(type="general-purpose", "研究竞品A产品定位...")
  → spawn Agent(type="general-purpose", "研究竞品B技术架构...")
  → spawn Agent(type="general-purpose", "研究竞品C定价策略...")
  → spawn Agent(type="Explore", "搜索项目中相关资料...")

每个 sub-agent:
  - 拥有独立的 200K context window
  - 完成后仅返回摘要给主 agent
  - 中间过程不污染主会话

用户看到的:
  🔄 正在从 4 个维度并行分析...
  ├─ ✅ 产品定位分析 (完成)
  ├─ ⏳ 技术架构对比 (进行中 72%)
  ├─ ⏳ 定价策略对比 (进行中 45%)
  └─ ⏳ 内部资料搜索 (进行中 30%)
```

Token 消耗：社区实测多 agent 工作流约为单 agent 的 **4-7 倍**。

### 核心 UI 设计原则：展现「能力」和「输出物」，隐藏「工作方式」

| 类型 | 举例 | 在 UI 中 | 原因 |
|------|------|---------|------|
| **输出物** | PPT、Word、Excel、PDF | ✅ **展现**为按钮+建议 | 用户需要知道"能得到什么"。不展现则大部分非技术用户根本不会想到可以要求这些输出。 |
| **分析能力** | 数据探索、趋势预测、对比分析 | ✅ **展现**为工具箱项 | 用户需要知道"能分析什么"。按业务场景组织。 |
| **工作方式** | 深度调查、并行研究、多 Agent | ❌ **不展现** | Claude 自主决策何时用。展现为按钮会产生虚假控制感。 |
| **执行过程** | Sub-agent 并行进度 | ⚠️ **只展现进度** | 用户需要知道"在做什么"，但不需要触发或控制。 |

### 为什么「深度调查」不该做成按钮

**问题1：虚假控制感**

如果做成按钮，用户以为点了就会"更深入"。但实际上 Claude 根据任务复杂度自主决定要不要 spawn agent。简单问题即使点了"深度调查"按钮，Claude 也不会硬 spawn agent——因为没必要。用户会困惑："我点了深度调查，为什么感觉和普通分析一样？"

**问题2：阻碍正常使用**

按钮的存在暗示"不点 = 不深入"。但实际上只要用户把问题描述清楚具体，Claude 自己就会判断需要深度研究并自动 spawn agent。按钮反而让用户以为不点就得不到深度分析。

**问题3：真正决定分析深度的是问题描述，不是按钮**

```
浅层结果: "分析竞品"
  → Claude 给一个概述，不 spawn agent

深层结果: "从产品功能、定价策略、目标市场三个维度，
           对比我们和竞品A、竞品B的差异"
  → Claude 自动 spawn 3 个 agent 并行研究三个维度
```

### 正确的做法：引导用户说清楚需求

与其给"深度调查"按钮，不如在**输入引导**上下功夫：

```
用户输入: "分析竞品"

智能提示（输入框下方）:
  💡 提供更多细节可以获得更深入的分析:
  "从产品功能、定价策略、目标市场三个维度，
   对比我们和 [竞品名] 的差异"
```

这比任何"模式开关"都有效——因为 Claude 是根据问题的**具体程度和复杂度**来决定调度策略的。

### 工具箱分类最终原则

```
✅ 按「能做什么 / 能得到什么」组织
  📊 数据分析
  📈 预测建模
  📋 报告与输出（PPT / Word / Excel / PDF）
  🔧 文档处理
  🏭 行业专用

❌ 不按「怎么做」组织
  🔍 深度调查   ← 不要
  ⚡ 快速分析   ← 不要
  🤖 多Agent模式 ← 不要
  📊 单次查询   ← 不要
```

## 17. 与 Claudeck 和 Claude Code Templates 的对比

社区已有一些 Web UI 项目尝试解决类似问题：

**Claudeck**（5天前发布）: 
- 自动发现 `.claude/commands/` 和 `.claude/skills/`
- 16个内置模板，点击填表发送
- 成本分析面板
- 插件系统（可用 Claude Code 自动生成插件）
- **不足**: 面向开发者设计，模板是技术模板而非业务场景

**Claude Code Templates**（by Daniel Avila）:
- 精美 UI，用量仪表板
- 从 slash commands 到 hooks 到 agents 全覆盖
- **不足**: 是开发者的配置管理工具，不是终端用户界面

**我们的方案不同之处**:

| 维度 | Claudeck / CCT | 我们的工具箱 |
|------|---------------|------------|
| 目标用户 | 开发者 | 非技术员工 |
| 技术暴露 | 展示 SKILL.md、frontmatter、YAML | 完全隐藏 |
| 分类逻辑 | 按技术分类（workflows/tools） | 按业务场景分类（数据分析/报告/预测）|
| 触发方式 | 输入 `/command-name` | 点击按钮 + 智能建议 + 自动触发 |
| 管理员层 | 无 | 完整管理员后台 |
| 多部门支持 | 无 | 按部门控制技能可见性 |

## 18. 总结

```
非技术用户的体验旅程:

[基础使用]
1. 打开浏览器 → 看到欢迎页、4个快速任务、⭐ 我的技能
2. 拖入 Excel → 系统自动识别并建议"分析/清洗/生成报告"
3. 点击"📊 分析数据" → Agent 开始工作
4. 看到任务树进度 → 知道 Agent 在做什么
5. 分析完成 → 看到结果 + 建议"📈 预测/📋 报告/📊 PPT"
6. 点击"📋 生成报告" → Agent 生成 Word 文档
7. 下载报告 → 完成

[能力扩展 — 从消费者变成创造者]
8. 用户发现这个分析每周都要做
9. 告诉 AI："把这个流程做成一个可重复的工具"
10. Claude 引导确认细节 → 自动创建 Skill
11. 下次打开 → ⭐ 我的技能中多了「周报-OEE分析」
12. 一键触发 → 和之前完全一样的分析流程
13. 觉得好用 → 点击"📤 分享给团队"
14. 管理员审核通过 → 全公司可用

整个过程中用户:
  ✅ 不需要知道什么是 slash command
  ✅ 不需要知道什么是 SKILL.md 或 YAML
  ✅ 不需要知道什么是 MCP 或 sub-agent
  ✅ 不需要安装任何东西（社区安装也是对话式的）
  ✅ 不需要记住任何命令
  ✅ 看到自己能做什么（工具箱 = 公共 + 个人）
  ✅ 被引导做下一步（智能建议）
  ✅ 知道 Agent 在做什么（任务树）
  ✅ 能把重复工作固化成自己的专属工具
  ✅ 能从社区安装现成工具扩展能力
  ✅ 能分享好用的工具给全公司

管理员:
  ✅ 控制共享 skill 的安装/可见性/触发方式
  ✅ 设置用户自创 skill 的安全策略
  ✅ 审核用户提交的"分享给团队"请求
  ✅ 维护社区安装的白名单源
  ✅ 监控用量和费用
  ✅ 个人 skill 隔离在用户工作区，互不影响

核心架构理念:
  管理员提供「基础能力 + 安全边界」
  用户在安全边界内「自由扩展能力」
  好的个人 skill 通过审核成为公共 skill
  平台的能力随使用越来越强，而非静态固定
```
